# Scheduler Web App — Low-Level Design (LLD)

Companion to HLD.md. Work in progress.

## 1. Environment & hosting

- **Project structure:**
  - `app.py` (Flask app, routes and database helpers for now) in the project root
  - `templates/` and `static/` in the project root, beside `app.py`
  - `database/` holds the SQLite file (`database.db`, ignored by Git)
  - `scripts/` holds one-off scripts, e.g. `db_creation.py` (standalone table creation)

- **Build locally first** on the laptop (Flask's development server).
- **Deploy later:** code on GitHub; Vercel deploys from the GitHub repo.
- **Database:**
  - Local: SQLite, accessed with Python's built-in `sqlite3` (plain SQL, no ORM).
  - Hosted (at deployment): **Turso** (hosted SQLite). The SQL stays the same; the connection code changes. Check Turso's free plan when deploying.
- Note: Vercel runs Flask as serverless functions with a read-only filesystem, so a local SQLite file cannot be used in production. That's why Turso is needed.

## 2. Data model

Dates and times are stored in **IST**, as **ISO 8601 text** (dates `YYYY-MM-DD`, times `HH:MM:SS`).
Column types below are as declared in `scripts/db_creation.py`. SQLite accepts `DATE`, `TIME` and `BOOLEAN` as type names but has no such types: `DATE`/`TIME` columns get NUMERIC affinity (the ISO text is still stored as text), and `BOOLEAN` values are stored as `0`/`1`.

| Table | Columns (all `NOT NULL`) | Keys & constraints |
|---|---|---|
| **Poll** | `poll_id` TEXT, `poll_name` VARCHAR(255), `participant_limit` INTEGER, `start_date` DATE, `start_time` TIME, `deadline` TIME, `password_hash` VARCHAR(255) | Primary key: `poll_id` |
| **PollDate** | `poll_id` TEXT, `date` DATE | Primary key: (`poll_id`, `date`) · Foreign key: `poll_id` → Poll |
| **Participant** | `participant_id` TEXT, `poll_id` TEXT, `participant_name` VARCHAR(255) `COLLATE NOCASE`, `is_creator` BOOLEAN | Primary key: `participant_id` · Foreign key: `poll_id` → Poll · `UNIQUE (poll_id, participant_name)` |
| **Selection** | `poll_id` TEXT, `participant_id` TEXT, `date` DATE, `slot_start_time` TIME | Primary key: (`poll_id`, `participant_id`, `date`, `slot_start_time`) · Foreign keys: `poll_id` → Poll, `participant_id` → Participant |

### Design decisions
- **Derived values are not stored:** the number of dates and the number of participants are counted when needed.
- **Dates** live in their own table (one row per date), not as JSON. The creator enters a **date range**; the code expands it into one PollDate row per day (look up `timedelta`).
- **The creator** is a row in Participant with `is_creator` = true. Their name is stored only there.
- **The password hash** lives on the Poll.
- **Participant ID** is `TEXT`, generated by the code.
- **Poll ID** is `TEXT`: a random, unguessable token generated by the code (`secrets` module), since it appears in the shared link.
- **Participant ID identifies a row, not a person.** The same name in two polls = two rows.
- **Names are unique within a poll**, case-insensitive. Enforced by the database via a composite unique constraint on (poll ID, name) with `COLLATE NOCASE`.
- **Selection uses long format:** one row = one participant is free for one half-hour slot on one date. A row existing means "free"; no flag column.
- **Poll ID on Selection** is a deliberate denormalization for simpler queries. Always take it from the participant's own poll ID, so the two never disagree.
- **Grid size:** 4 AM – 11 PM = 38 half-hour slots per date. Worst case ≈ 5 dates × 38 slots × participants rows per poll; fine for SQLite.
- Deadline changes (end early / shorten) are just updates to the Poll's deadline.

### Operations
- **Updating selections (before the deadline):** the code deletes the participant's existing Selection rows, then inserts the new set.
- **Removing a participant (creator, before the deadline):** find the participant → delete their Selection rows first → then delete the Participant row. Done by code (not `ON DELETE CASCADE`, for now).
- Both operations run inside a **transaction** so either every step happens or none does.

## 3. Pages and actions

### Pages (3)
1. **Main / Login page** (the home page)
   - Name box, poll ID box, Submit.
   - Poll ID is pre-filled when opened from a shared link; otherwise it's typed in.
     (Two routes: one with the poll ID in the URL, one without.)
   - If the name belongs to the creator, the same page reloads with a **password box** added; name and poll ID stay filled in.
   - A **"Create new poll"** button.
2. **Create poll page**
   - Creator name, poll name, participant limit, **start date and end date** (a date range), response window (hours), password, Submit.
   - The server re-checks the dates: both present, start not in the past, end on or after start, at most 5 days, none before the deadline.
   - After Submit: the creator lands on the **login page with the poll ID filled in** and logs in with name + password.
3. **Poll page**
   - Header "Scheduling: <poll name>", countdown, grid, **Save** button (grid only).
   - **Left panel (creator only):** the share link, plus the creator controls.
   - **Right panel (creator only):** the participant list, each with a Remove button.
   - After the deadline, the **result** is shown on this same page.

### Actions (7), each with its own button and route
1. Create poll
2. Log in (including the password step)
3. Save selections
4. Remove a participant (creator)
5. Raise the participant limit (creator)
6. Shorten the deadline (creator)
7. End the poll now (creator)

- Pages are shown with **GET**; actions send data with **POST**, then redirect (Post/Redirect/Get).
- No "Are you sure?" confirmations in the trial version.
